# 프레임 방식 2판: 위치 측정 + 드론끼리 방송 + 기록 (2026-11-24)

6대 실측 실험용 통신 펌웨어입니다. 20 ms 프레임마다 태그 한 대가 7패킷으로 위치를 재고, 차례인 드론이 heartbeat 를,
일정에 적힌 드론이 추가 슬롯을 방송합니다. 내용은 실제 크기의 빈 데이터입니다. 모든 줄에 프레임 번호가 붙습니다.

**실제 앵커와 태그로는 아직 돌려 보지 않았습니다.** 빌드와 PC 모의시험까지 했습니다. 보드에서는 새 태그 펌웨어가 켜져서
`TF_INFO,fw=tagf-v2,...` 를 내는 것만 봤습니다(앵커 없이).

1판(11-24 낮에 올린 `tagf-v1`, `anchorf-v1`)과는 섞어 쓸 수 없습니다. 앵커와 태그를 모두 2판으로 올리세요.

## 1. 한 프레임

앵커 1 의 질문 패킷(Poll)이 프레임의 시작입니다. 아래 시각은 그 패킷 기준이고 기본값(S 600, D1 900, D2 700, post 1000, frag 600, xchg 700 µs)일 때입니다.

| 구간 | 시각 µs | 보내는 쪽 |
|---|---|---|
| 위치 측정 7패킷 | Poll 0, 600, 1200 / Response 2100 / Final 2800, 3400, 4000 | 앵커 3대와 차례인 태그 |
| heartbeat (조각 2개) | 5000, 5600 | 차례인 태그 |
| 추가 슬롯 j = 1 ~ K (방송: 조각 2개) | 5000 + 1200 j, 그 600 µs 뒤 | 일정의 주인 (차례 + j 번 태그) |
| 추가 슬롯 (교환: 패킷 3개) | 6200 + 2100 (j − 1), 700 µs 간격 | 주인 → 상대 → 주인 |
| 조용한 구간 | 무선이 끝난 뒤 ~ 다음 프레임 1.5 ms 전 | 제어 계산, 기록 만들기, SD 쓰기 |

- 방송 하나는 빈 데이터 180바이트(조각마다 110바이트 패킷에 90바이트). 교환 패킷은 60바이트입니다.
- 추가 슬롯 5개(여섯 대 모두 매 프레임 방송)일 때 무선은 11.76 ms 에 끝납니다(모의시험). 한도는 12 ms 입니다.
- 설계서의 "방송 0.75 ms"보다 넓게 잡았습니다(방송 하나 1.2 ms). 다음 슬롯의 주인이 앞 조각을 다 듣고 송신을 예약할 시간이
  모의시험에서 모자랐기 때문입니다. 실제 보드에서 여유가 보이면 앵커 1 의 `--frag-us` 로 줄입니다.
- 앵커 1 의 Poll 을 못 받은 태그는 그 프레임에 아무것도 보내지 않습니다. 듣고 기록하는 일은 계속합니다.

## 2. 앵커 (DWM3001CDK)

앵커는 펌웨어를 올린 뒤 **명령 없이 전원만 넣어 둡니다**(보조 배터리). 설정은 모두 앵커 1 을 빌드할 때 정하고,
앵커 2, 3 과 태그는 앵커 1 의 Poll 에 실린 값을 따릅니다. 설정을 바꾸려면 앵커 1 만 다시 올립니다.

```powershell
py flash.py --list
py flash.py --packets f --id 1 --serial 000760226397            # 기본: 추가 슬롯 1, 대본 없음
py flash.py --packets f --id 2 --serial 000760226502
py flash.py --packets f --id 3 --serial <A3 의 J-Link 번호>
py flash.py --packets f --id 1 --variant k3 --serial 000760226397    # 설정이 다른 앵커 1
```

미리 빌드해 둔 앵커 1 의 판(`build/f/A1_<이름>/`)과 대본은 `README_FLIGHT_KO.md` 2장의 표에 있습니다.
SHA-256 과 설정은 각 폴더의 `manifest.json` 에 있습니다.

앵커 1 의 빌드 옵션 (`py build.py --packets f --id 1 --variant <이름> ...`)

| 옵션 | 기본 | 뜻 |
|---|---|---|
| `--extra` | 1 | 프레임당 추가 슬롯 수. 0, 1(30대에 해당), 3(16대에 해당), 5 |
| `--exchange` | 끔 | 추가 슬롯을 교환(패킷 3개)으로 |
| `--coord-drone` | 끔 | 일정을 드론 0번이 따로 방송 (설계서 5절의 비교 설정) |
| `--post-us`, `--frag-us`, `--xchg-us` | 1000, 600, 700 | 위치 측정 뒤 heartbeat 까지, 방송 조각 사이, 교환 패킷 사이 |
| `--script`, `--script-start`, `--script-speed`, `--script-limit`, `--script-mover` | 0, 1500, 30, 50, -1 | 대본 (`README_FLIGHT_KO.md`) |
| `--s-us`, `--d1-us`, `--d2-us` | 600, 900, 700 | 위치 측정의 S, D1, D2 |

무선 시간이 프레임의 60 % 를 넘는 조합은 빌드가 되지 않습니다(예: 교환 5개).

앵커가 내는 줄(J-Link VCOM, 115200)은 1판과 같고, `A?_BOOT` 에 설정이, `A?_STAT` 에 `drone=`(들은 드론 패킷 수)이 붙었습니다.

## 3. 태그 (NUCLEO-N657X0-Q + DWM3000EVB)

| 판 | 파일 (`tag/build/`) | 쓰는 때 |
|---|---|---|
| USB 기록 | `stm32_projects_FSBL_tagf_v2_id<번호>_O2.elf` | 받침 위, USB 로 기록 |
| SD 기록 | `stm32_projects_FSBL_tagf_v2_id<번호>_sd_O2.elf` | 받침 위, SD 에도 기록 |
| 비행용 | `flight/n6_flight_tagf_v2_id<번호>-trusted.bin` | 드론에 올림 (`README_FLIGHT_KO.md`) |

번호는 0~5, 드론마다 달라야 합니다. SHA-256 은 `tag/build/SHA256_tagf_v2.txt`, `tag/build/flight/SHA256.txt`.

```powershell
py tools\frame_measure.py --ports COM5 COM6 COM7 --seconds 120 --out results\stage0     # 창 1: 먼저 기록을 켠다
py tools\load_tag.py tag\build\stm32_projects_FSBL_tagf_v2_id0_O2.elf --sn <ST-LINK 번호>   # 창 2: 태그마다 자기 번호의 ELF
```

- 앞의 둘은 RAM 에 올리는 판입니다(전원을 끄면 사라짐). **태그의 USB 속도는 921600 bit/s 입니다**(1판은 115200).
- 확인할 출력: `TF_READY,channel=5`, `TF_INFO,fw=tagf-v2,id=0,tags=6,...`, 그 뒤 프레임마다 `F,...` 와 `P,...` 줄.

## 4. 기록의 줄

```
F,<프레임>,<기준 시각>,<차례>,<들은 것>,<Response>,<Response 여유 µs>,<되돌림 µs>,<수신오류>,<일정>,<추가 슬롯 수>,<표시>,
  <무선 끝 µs>,<조용한 구간에 쓴 µs>,<그중 가장 긴 한 번 µs>,<기록 버림 누계>,<제어 계산 시작 µs>,<제어 계산 끝 µs>,<다 받은 방송 수>
R,<프레임>,<앵커>,<mm>,<거리 유효>,<끝 종류>,<Final RSSI>,<Final 첫경로>,<Poll 시각>,<Poll→Final ns>
P,<프레임>,<종류>,<방향>,<슬롯>,<조각/단계>,<보낸 태그>,<받는 태그>,<일련번호>,<바이트>,<성공>,<예약 µs>,<어긋남 ns>,<칩 시각>,<RSSI>,<첫경로>,<시계 차이>
K,<프레임>,<제어 번호>,<표시>,<추가 슬롯 수>,<post>,<frag>,<xchg>,<대본>,<명령>,<시작 프레임>,<움직일 태그>,<속도>,<한도>,<S>,<D1>,<D2>
L,<프레임>,<1 켬 / 0 끔>
S,<프레임>,<기록 버림>,<수신오류 누계>,<기타 패킷 누계>,<다른 방식 패킷 누계>
D,<프레임>,<SD 상태>,...                                                       (SD 판)
C, E, U                                                                         (비행용. README_FLIGHT_KO.md 5장)
```

칸의 뜻은 `tag/tag_f.c` 머리말에 다 있습니다. 여기에는 쓰임만 적습니다.

- `P` 는 내가 보낸 패킷(방향 T)과 받은 패킷(방향 R)마다 한 줄입니다. 종류는 H heartbeat, B 추가 슬롯 방송, X 교환, C 일정.
- `K` 는 앵커 1 이 보낸 설정이 바뀔 때(켤 때, 앵커 1 이 다시 켜질 때)마다 한 줄. 비행의 설정 기록입니다.
- `L` 은 영상과 맞추는 LED(NUCLEO 의 파란 LED)가 켜지고 꺼진 프레임입니다. 5초마다 0.1초, 60초마다 1초 켭니다.
- 받은 쪽의 "어긋남"은 앵커 1 의 Poll 을 받은 내 시각 기준입니다. 그 Poll 을 못 받은 프레임이면 2147483647 입니다.
- 보낸 쪽의 "어긋남"은 예약한 값으로 적습니다(예약 송신은 그 시각에 나가거나 아예 실패하므로 0 에서 8 ns 안). 예약이 늦어 못 보내면 성공 칸이 0 입니다.

설계서의 "기체 기록만으로 나오는 값"이 어느 칸에서 나오는지

| 값 | 기록 |
|---|---|
| 앵커와의 손실, 드론 사이의 손실, 연달아 잃는 길이 | `F` 의 들은 것, `R`, 보낸 쪽 `P…T` 와 받은 쪽 `P…R` 을 프레임·슬롯·조각·일련번호로 맞춤 |
| 전달 확률 | 위 손실 기록에 시뮬레이터의 추정식을 돌림 (분석 도구 15장) |
| 시계 오차 | `P` 의 시계 차이(칩이 알려 주는 값)와 칩 시각, `F` 의 기준 시각에서 구한 프레임 간격 |
| 보호 시간 | `P` 의 어긋남 (받은 쪽), 예약이 늦은 횟수 |
| 받은 패킷이 쓰이기까지의 시간 | `F` 의 제어 계산 시작 − `P` 의 (예약 µs + 어긋남) |
| 계산 시간 | `F` 의 제어 계산 끝 − 시작. 이 실험에는 알고리즘이 없어 빈 계산의 길이입니다 |
| 명령이 반영되는 지연 | `C` 의 명령 칸과 속도 칸 (비행용) |

## 5. SD 카드 기록

**카드 준비** (PC 에서, 한 번)
1. 카드를 FAT32 로 포맷합니다(32 GB 이하).
2. 포맷한 직후에 `py tools\sd_prepare.py --drive E:\` 로 `UWBLOG.BIN`(256 MiB, 0 으로 채움)을 만듭니다.
3. 카드를 보드에 꽂습니다. **캐리어 보드에 전원이 들어가야** 카드가 켜집니다.

**동작**
- 태그는 파일 시스템을 고치지 않고, 그 파일이 차지한 자리에 차례로 씁니다. 켤 때마다 앞 기록 뒤에 이어 씁니다.
- 카드에 쓰기를 거는 일(약 0.3 ms)과 줄을 글자로 만드는 일은 프레임의 조용한 구간에서만 합니다.
- 0.5 s 동안 한 섹터가 안 차면 줄바꿈으로 채워서 씁니다. 전원이 갑자기 꺼지면 마지막 0.5 s 쯤을 잃습니다.
- 시작할 때 `TF_SD,ready=1,card=1,...,file=ok,...,next_block=N` 이 나와야 합니다.
  - `file=no_file` : 카드에 `UWBLOG.BIN` 이 없음. `file=fragmented` : 파일이 조각남(포맷하고 다시 만들기).
  - `card=0` : 카드가 응답하지 않음(카드 없음, 캐리어 전원 없음).
- 256 MiB 는 추가 슬롯 1개 설정에서 약 4시간, 5개에서 약 2시간 분량입니다(줄 길이로 어림한 값, 재지 않음).

**꺼내기** (PC 에서)
```powershell
py tools\sd_extract.py --file E:\UWBLOG.BIN --out results\flight1
py tools\frame_measure.py --tag-logs results\flight1\tag*_run*.raw.log --out results\flight1
```
- 켠 횟수마다 `tag<번호>_run<순서>.raw.log` 로 나뉩니다. 여섯 장의 카드를 같은 폴더에 꺼내면 한 번에 분석됩니다.
- 기록을 지우려면 `py tools\sd_prepare.py --drive E:\ --overwrite`.

## 6. 분석 도구

```powershell
py tools\frame_measure.py --ports COM5 COM6 COM7 --anchor-ports COM8 --seconds 120 --out results\stage0   # 기록하면서
py tools\frame_measure.py --tag-logs results\stage0\port*.raw.log --anchor-logs results\stage0\anchor*.raw.log --out results\stage0
py tools\frame_measure.py --tag-logs sd\tag*_run*.raw.log --guard-margin-us 50 --out results\flight1          # SD 에서 꺼낸 것
```

여섯 기체(와 앵커)의 기록을 프레임 번호로 합쳐 표 17장과 파일을 냅니다.

| 장 | 내용 |
|---|---|
| 1~6 | 프레임 수신, 앵커별 Poll 수신율과 연달아 잃은 길이, 위치 측정, Response 엿듣기, 앵커 기록 링크, 시각 |
| 7~9 | 드론→드론 방송(방향별 손실, 연달아 잃은 길이), 교환, 일정 |
| 10~12 | 예약 시각과 실제 시각의 차이, 프레임당 무선 시간과 드론별 1초 송신 시간, 태그 사이 시계 차이 |
| 13~14 | 조용한 구간에 쓴 시간, 제어 계산 시간, 받은 패킷이 쓰이기까지의 시간, 이웃 정보가 오래된 정도 |
| 15~16 | 전달 확률 추정식의 적중률, 손실 모형의 값 |
| 17 | 비행 제어기 값과 사건, 명령이 반영되는 지연, 모르는 줄 |

파일: `frame_summary.txt/.json`, `ranges.csv`, `frames.csv`, `packets.csv`, `links.csv`, `sync_led.csv`(영상과 맞추기),
`flight.csv`, `events.csv`, **`sim_params.json`**(시뮬레이터에 넣을 값).

읽을 때 주의
- 손실은 보낸 쪽 줄과 받은 쪽 줄을 맞춰 셉니다. 기록이 버려지면 손실이 실제보다 크게 나오니 1장과 13장의 "기록 버림"이 0 인지 먼저 보세요.
- 보낸 쪽 기록이 없는 태그는 일정으로 추정하고 "추정"으로 표시합니다. 이때는 그 태그가 기준을 놓쳐 안 보낸 것도 손실에 섞입니다.
- `sim_params.json` 의 패킷 시간과 교환 시간은 패킷 길이와 설정으로 **계산한** 값입니다. 잰 값은 위치 측정 시간, 어긋남, 손실, 시계, 계산 시간입니다.
- 보호 시간은 "어긋남 절댓값의 99 % + `--guard-margin-us`"이고 여유의 기본은 0 입니다. 여유를 얼마로 할지는 정해 주셔야 합니다.
- 전달 확률 추정식은 시뮬레이터 `mac.py` 의 `_p()`(p ← 0.9 p + 0.1 × 받음, 처음 0.7)입니다. "p ≥ 0.5 면 받는다고 예측"이라는 판정 기준은 도구가 정한 것입니다.
- 시계 차이의 부호는 칩이 주는 값 그대로입니다. 실제 칩에서 어느 쪽이 양수인지는 확인하지 않았습니다.
- 교환은 상대 태그도 그 프레임의 Poll 을 받아야 답합니다. 손실 5 % 의 모의시험에서 세 패킷이 다 된 비율이 0.95⁴ 로 나옵니다.

## 7. 확인한 것과 안 한 것

확인한 것
- 빌드: 앵커 3대와 앵커 1 의 판 15개(`-O2 -Wall -Wextra -Werror`), 태그 18개(CubeIDE Debug `-O2`, 오류 0·경고 0).
- 9패킷과 7패킷의 앵커 hex 는 그대로입니다.
- PC 모의시험 `python3 sim/run_sim.py`: **308개 통과**. 펌웨어 C 소스를 그대로 컴파일해 태그 6대 + 앵커 3대로 돌립니다.
  2판에서 더한 것: heartbeat 와 추가 슬롯 1개·5개(조각이 시각표에서 3 µs 안, 겹침 0, 예약 늦음 0), 교환 3개,
  일정을 드론 0번이 보내는 설정(0번을 못 듣는 태그는 방송하지 않고 위치 측정은 계속), 손실 5 %,
  앵커 1 이 안 들리는 태그(아무것도 안 보냄).
- 분석 도구 `python3 tools/test_frame_measure.py`: 130개 통과(가짜 기록 96, 모의시험 34). 손실 5 % 모의시험에서 조각 손실 5.0 %, 방송 손실 9.7 %, 연달아 잃는 평균 길이 1.11.
- 보드 한 장: USB 기록판이 켜져 `TF_INFO,fw=tagf-v2` 를 921600 bit/s 로 냄. SD 읽기·쓰기는 1판 때 확인(`sdcheck/README_KO.md`).

안 한 것
- **앵커와 태그를 실제로 같이 돌리는 것 전부.** 모의시험의 SPI 시간, 칩의 수신 켜는 시간은 어림값입니다. 특히
  - 방송 조각을 받고 600 µs 뒤의 다음 조각을 받을 수 있는지(수신을 다시 켠 뒤에 신호 세기를 읽습니다. 칩에서 그 값이 유효한지 확인 못 함)
  - 예약이 늦는 일(`P` 의 성공 0)이 실제로 없는지
- 카드에 `UWBLOG.BIN` 을 만든 상태에서 태그가 그 파일을 찾아 쓰는 것, 무선과 SD 쓰기가 같이 도는 것.
