# A 묶음 작업: 원본 기록·10Hz 개선·불확실성·반복 검증

기준일: 2026-10-14. 기준 펌웨어는 기존 `a04e2c93348cad9c135f5d691ea1bf4ecba10c02`를 유지했다. 펌웨어를 수정하거나 재빌드하지 않았다.

3. `sensor_bridge`: 선택적 `--record` 진단을 추가했다. 영상 자체는 저장하지 않고 영상 시각·프레임 간격·계산 시간·광류·품질·거리 데이터를 저장한다. 센서 계산 공식은 바꾸지 않았다.
4. CSV에 예약 시각·건너뛴 슬롯·새 추정 표본 여부를 추가했다. 기존 B 공통 열은 유지했다.
5. MAVProxy `--streamrate -1`로 주기 요청 간섭을 제거했다. 메시지별 주기는 Fleet에서 관리한다.
6. `analyze_raw.py`, `plot_raw.py`: 원본 수신 주기와 단계별 오차·기울기·광류 품질·방향 오차를 분석한다.
7. 현재 빌드의 `UTM_GLOBAL_POSITION` 불확실성 요약을 수신했다. 전체 공분산과 별도 필드로 제공한다.
8. `run_a_batch.py`: 순차 반복 비행, 성공/실패 및 10Hz 검사 결과를 manifest에 저장한다.

## 주기 문제의 원인과 확인

기존 CSV는 현재 수신 시각을 다음 간격의 기준으로 다시 삼아 지연이 누적됐다. 고정된 0.1초 슬롯으로 바꾸자 약10Hz가 됐다. 늦은 슬롯은 표시하고 가짜 데이터로 채우지 않는다.

그러나 원본 LOCAL_POSITION_NED는 8.0~8.3Hz였다. 설치된 MAVProxy의 `set_stream_rates()`가 기본4Hz `REQUEST_DATA_STREAM`을 반복 전송하는 반면, Fleet은 10Hz `SET_MESSAGE_INTERVAL`을 요청했다. MAVProxy의 주기 요청만 끈 비교 실행에서 원본 수신이 약10Hz로 바뀌었다.

회귀 확인 명령은 `analyze_raw.py <실행폴더> --require-10hz`다. 원본 추정 수신과 CSV의 관측 주기가 각각9.5Hz 이상이어야 통과한다. 기존 기준 실행은 실패, 수정 후 네 회차는 모두 통과했다. 이는 시뮬 시간 기준이며 실제 벽시계 기준 실시간10Hz 보장은 아니다.

## 불확실성: 확보한 것과 아직 없는 것

현재 ArduPilot 소스 `AP_NavEKF3_Outputs.cpp`의 `getPosVelUncertainty()`는 실제 상태 공분산 P에서 수평 `sqrt(P[7][7]+P[8][8])`, 수직 `sqrt(P[9][9])`, 속도 성분 중 최대 표준편차를 반환한다. `GCS_Common.cpp`의 `send_utm_global_position()`이 이를 `h_acc`, `v_acc`, `vel_acc`로 내보낸다.

`fleet_api.get_estimate()`의 `accuracy_summary`에서 `h_acc_m`, `v_acc_m`, `vel_acc_mps`, `source`, `valid`를 확인한다. 값0과 포화65535는 사용할 수 없는 요약으로 처리하고 수신 후2초 이상이면 무효다. 최종 단일 기체에서382개를 수신했고 초기화 값을 제외한372개가 사용 가능한 값이었다.

이 의미는 **검증한 현재 빌드**에 근거한다. 다른 펌웨어의 같은 메시지까지 동일 의미라고 가정하지 않는다. 수평 요약을 x/y 분산으로 절반씩 나누지 않는다. `position_cov_enu_m2=None`, `uncertainty_valid=False`는 그대로다. 전체 3×3 위치 공분산은 여전히 미완료다.

이름이 비슷한 `getVariances()`는 innovation consistency test ratio를 반환하므로 위치 공분산 대신 쓰지 않는다.

## 오차 진단에서 확인한 범위

- 카메라/거리 입력은 기준 실행에서 약30Hz였다. 광류 계산 호스트 시간의95백분위는 약4.4ms였다.
- 이동 구간의 광류 품질0 현상은 기준 정사각형에서 없었다. 따라서 지속적인 품질0을 주원인으로 단정할 근거는 없다. 높은 품질 값이 실제 속도 정확도를 보장하지는 않는다.
- 방향 차이의 단계별 중앙값은 대체로 약0.1~1.4도 범위였다. 이것만으로 위치 드리프트를 설명했다고 주장하지 않는다.
- AP_OpticalFlow_MAV 드라이버는 AHRS 자이로를 bodyRate로 사용한다. 단순히 '자이로 보상 없음'이라고 단정하거나 브리지에서 이중 보상하지 않는다.
- 해당 드라이버는 OPTICAL_FLOW 패킷의 외부 time_usec 대신 수신한 AP 시각을 사용한다. 전달 지연·프레임 간격과 보상 시점의 일치는 후속 진단 대상이다.
