# 편대 리모트 대시보드 설계

작성일 2026-11-22. 상태: 사용자 승인(2026-11-22).

## 의도와 이유

드론 6대의 편대 비행을 노트북 한 대에서 조작하고, 그 결과를 3D 화면으로 보여주는 앱이다. 주 용도는 최종 발표 시연이다. 청중이 버튼 하나를 누르면 화면 속 드론이 그 명령대로 움직이는 것을 바로 이해해야 한다. 장기적으로는(다음 단계) 같은 앱이 실기체에도 명령을 보내고, 화면이 실기체의 상태를 보여준다.

실기체는 아직 호버링에 성공하지 못했고, 공통 위치 좌표계와 6대 동시 연결도 갖춰지지 않았다. 그래서 가상 모드와 실기체 모드를 나누고, **첫 버전은 가상 모드만 만든다.** 가상 모드는 `swarm/`의 편대 제어와 충돌 회피 계산으로 드론을 움직인다. 실기체 모드는 기체에 필요한 요소가 갖춰진 뒤 같은 화면에 붙이는 다음 단계다. 발표 때는 두 모드를 동시에 보여주지 않고 하나만 골라서 보여준다.

## 목표

- 화면 중앙에 3D 쿼드콥터 6대가 있고, 버튼으로 시작, 중지, 편대 형태 변경, 복귀를 명령한다.
- 명령을 내리면 3D 화면의 드론이 그 형태로 움직인다.
- 첫 버전은 가상 모드만 동작한다. 서버가 기체를 "기체 백엔드"라는 하나의 틈으로 다뤄서, 나중에 실기체 백엔드를 화면 수정 없이 붙일 수 있게 한다.
- 발표 노트북에서 명령 한 줄로 서버를 켜고 브라우저로 연다. 인터넷 없이 동작한다.

## 목표가 아닌 것

- 2D 지도, 알고리즘 패널, 로그 화면. 첫 버전에는 넣지 않는다. 사용자가 B안(전체 화면 3D)을 골랐다.
- 로그인, 다중 사용자, 원격 접속.
- 비행 로그 분석이나 파라미터 편집. 기존 `tools/`가 맡는다.
- 실기체 모드(BLE 연결, MAVLink 명령, 실기체 안전 처리), 모드 전환 스위치, 비상 정지 버튼. 첫 버전에서는 만들지 않는다. 아래 "다음 단계: 실기체 모드"를 본다.
- `swarm/simulator.py` 수정. 기존 시뮬과 테스트는 그대로 둔다.

## 실패로 보는 경우

- 발표 중 인터넷이 없어서 화면이 안 뜬다.
- 화면에 지어낸 값(가상 배터리 등)이 실측처럼 보인다.
- 편대를 바꿀 때 드론들이 서로 엉켜 지나가서 청중이 형태를 알아보기 어렵다.
- (다음 단계) 화면은 움직이는데 실기체에는 명령이 안 나가거나 그 반대인데 사용자가 모른다. 가상 모드인데 실기체에 명령이 나간다.

## 제약

- 첫 버전은 기체와 통신하지 않는다. BLE나 MAVLink 코드를 넣지 않는다.
- (다음 단계) 레포 규칙: 기체에 arm, 이륙, 모터 명령을 보내는 시험은 사용자가 정한 절차에서만 한다. 개발 중 시험은 프롭을 뗀 상태에서만 하고, 내가 임의로 arm이나 이륙 명령을 보내지 않는다.
- (다음 단계) 기존 안전 설계를 따른다. `tools/n6_fly.py`가 연결 중 0.2 초마다 지상국 HEARTBEAT를 보내서 링크가 끊기면 FC가 3초 뒤 LAND한다. 모드가 GUIDED가 아니게 바뀌면 자동으로 GUIDED로 되돌리지 않는다.
- 현재 확인된 기체는 1호기와 4호기뿐이다. 노트북 한 대에서 BLE로 여러 기체를 동시에 연결하는 것은 검증되지 않았다. 드론 사이 통신 방식과 공통 위치 좌표계(UWB)는 기체에 아직 없다.
- 레포에 Claude 표기를 넣지 않는다. 커밋과 PR은 사용자가 요청할 때만 한다.

## 접근 방식

세 가지를 비교했고 1번으로 정했다.

1. **웹 화면 + PC 로컬 Python 서버 (선택).** 화면은 three.js, 서버는 Python이다. 둘은 WebSocket으로 통신한다. 서버가 `swarm/`의 계산 모듈을 재사용한다. 다음 단계에서는 `tools/n6_fly.py`가 쓰는 BLE와 MAVLink 경로로 기체와 통신한다. 노트북에서 서버를 켜고 브라우저를 열면 된다.
2. Electron이나 Tauri 데스크톱 앱. 1번에 껍데기만 더한 구조라 무겁고, 발표 직전에 빌드 문제가 생길 위험이 있다. 채택하지 않았다.
3. 웹 화면만 쓰고 Web Bluetooth로 직접 통신. 6대 동시 연결이 어렵고 `swarm/`의 Python 코드를 쓸 수 없다. 채택하지 않았다.

## 구조 (사용자가 정한 것과 내가 정한 것)

사용자가 정함: 위 1번 구조, 가상 모드와 실기체 모드 분리(첫 버전은 가상 모드만), 쿼드콥터는 코드로 만든 모양, 전체 화면 3D 위에 버튼과 라벨이 떠 있는 구성(B안), 파란색 계열 그리드 배경, 발표 때 모드 하나만 보여줌. 아래 "내가 정함" 항목도 사용자가 검토 후 그대로 반영하라고 했다.

내가 정함:

- 위치는 레포 루트의 `dashboard/`. 안에 `server/`(Python)와 `web/`(정적 파일)를 둔다.
- 서버 프레임워크는 FastAPI, 실행은 uvicorn(사용자가 정함). 많이 쓰는 도구라 팀원이 읽고 고치기 쉽다. 정적 파일은 `StaticFiles`, 통신은 FastAPI의 WebSocket으로 처리한다. asyncio 위에서 돌므로 다음 단계의 BLE(`bleak`)도 같은 서버에 붙일 수 있다. 지금 노트북에는 설치돼 있지 않다(`pip install fastapi uvicorn`).
- 서버는 드론을 "기체 백엔드" 하나로 다룬다. 첫 버전에는 가상 백엔드 하나뿐이다.
  - 가상 백엔드: 서버 안에 한 단계씩 진행하는 시뮬 루프를 둔다. `swarm/simulator.py`의 `run()`은 끝까지 한 번에 돌고 지표만 돌려주며 중간 위치를 꺼낼 수 없고 2D뿐이라서 그대로 쓰지 않는다. 대신 같은 계산 모듈을 재사용한다: `formation_control.formation_vel`(편대 속도), `collision_avoidance.cbf_qp`(충돌 회피), `collision_avoidance.Deadlock`(교착 완화). 운동 모델은 `simulator.py`와 같은 1차 지연(v' = (u − v) / τ)이다. 평면(x, y)은 이 계산을 따르고, 고도 z는 별도로 목표 고도까지 일정 속도로 올리고 내린다.
  - 실기체 백엔드(다음 단계): 기체마다 BLE 연결을 하나씩 열고, MAVLink로 텔레메트리를 읽고 명령을 보낸다. 첫 버전에서는 만들지 않는다.
- 서버가 화면으로 보내는 상태: 드론별 위치(x, y, z), 비행 상태(지상, 이륙 중, 호버, 착륙 중), 현재 편대, 현재 모드. 화면이 서버로 보내는 명령: 시작, 중지, 편대 선택, 복귀.
- 좌표: 시뮬은 x, y가 바닥 평면이고 z가 위다. three.js는 y가 위이므로 화면에서 축을 바꿔 그린다.
- three.js는 레포에 복사해 두고 버전을 고정한다. 본체와 함께 애드온 `CSS2DRenderer`(드론 위 번호 라벨)와 `OrbitControls`(카메라 조작)도 복사한다. CDN을 쓰지 않는다. 발표장에 인터넷이 없어도 동작해야 한다.

### 명령의 뜻 (가상 모드)

- 시작: 지상에 있는 드론이 이륙해 정해진 호버 고도에 머문다. 이미 떠 있으면 아무 일도 하지 않는다.
- 중지: 모든 드론이 그 자리에서 착륙한다.
- 편대 선택(일렬, 삼각, 원): 떠 있는 드론이 편대 중심을 유지한 채 새 형태로 이동한다. 지상에 있으면 형태만 기억해 두고 시작할 때 그 형태로 선다.
- 복귀: 드론이 시작 위치 위로 이동한다. 착륙은 하지 않는다. 착륙은 중지로 한다.
- 편대 자리 배정: 편대를 바꿀 때 각 드론을 가까운 자리부터 탐욕적으로 배정해 경로가 덜 엇갈리게 한다. 충돌은 CBF가 막는다.

### 화면

- 3D 장면이 화면 전체를 채운다.
- 배경: 평평한 어두운 남색 바탕에 파란색 네온 그리드. 바닥 그리드와 뒷벽 그리드가 있고, 원근감이 보인다. 그라데이션은 쓰지 않는다. 파란색 계열 한 가지 색조로 통일한다.
- 카메라: 편대에 맞춰 화면을 잡는다. 편대 반경은 약 1 m라서 15 m 방 전체를 보이면 드론이 점처럼 작아진다. 그리드는 실제 방 크기를 나타내지 않는 장식이다. 발표자가 마우스로 돌려볼 수 있다.
- 드론: 몸체, X자 팔 4개, 프로펠러 4개로 만든 쿼드콥터. 비행 중에는 프로펠러가 돈다. 드론 위에 번호 라벨이 떠 있다. 배터리는 표시하지 않는다. 가상 모드의 배터리 값은 지어낸 숫자라 발표 화면에서 실측처럼 보이면 안 된다.
- 버튼: 왼쪽에 편대 선택(일렬, 삼각, 원), 아래 중앙에 시작, 중지, 복귀. 위쪽에 서버 연결 상태, 현재 편대, 모드 표시. 편대 종류는 첫 버전에서 이 세 가지이고, `swarm/`의 육각은 구현 단계에서 넣을지 정한다.
- 서버 연결 상태: 화면과 서버 사이 WebSocket 연결을 뜻한다. 끊기면 화면 위에 "서버 연결 끊김"을 띄우고 자동으로 다시 연결을 시도한다.
- 색: 파란색 계열이 기본이다. 서버 연결 상태 점만 초록(연결), 빨강(끊김)을 쓴다.
- 모드 표시: 현재 모드를 화면 위쪽에 표시한다. 첫 버전에서는 "가상 모드"만 나온다.

## 추가 (2026-11-22): A* 경로 이동과 장애물

사용자가 요청했다: 고정 장애물과 클릭으로 놓은 장애물을 모두 피해 목표점까지 가는 것을 보여준다(C안).

- 방은 15 m x 15 m, 중심 (0, 0). 바닥 그리드가 실제 방 크기다. 고정 기둥 3개 (-3.5, 2.5), (3.0, -3.5), (1.0, 4.5), 반경 0.5 m.
- 왼쪽 도구: 목표 지정, 장애물 배치(둘 중 하나만 켜짐), 장애물 지우기(놓은 것만). 켠 상태에서 바닥 클릭이 목표나 장애물이 되고, 드래그는 카메라 회전이다.
- 목표를 찍으면 편대 중심에서 목표까지 `swarm.path_planning`의 A*로 계획한다. 장애물과 벽은 편대 반경 + D만큼 부풀린다. 편대는 `PathFollower`로 형태를 유지한 채 경로를 따라간다.
- 이동 중 장애물을 추가하거나 지우거나 편대를 바꾸면 현재 위치에서 다시 계획한다. 길이 막히면 제자리에 멈추고 알린다.
- 장애물은 CBF 제약에도 항상 들어간다(반경 + D). 복귀도 A*로 시작 위치까지 간다.
- 거부: 지상에서 목표 지정, 방 밖, 드론 위나 다른 기둥 위의 장애물, 들어갈 공간이 없는 편대. 화면 아래에 알림을 띄운다.
- 편대 자리 배정을 탐욕 배정에서 총거리 최소 배정(순열 전수)으로 바꿨다. 6가지 전환에서 경로 교차 3에서 0, 총거리 87 m에서 70 m. consensus 항은 연구 대상이라 그대로 둔다.
- 시험 후 고친 것 (무작위 시나리오 60회, 목표 237개):
  - 교착 완화 오작동: 직전 속도 대신 0을 넘겨 1초마다 교착으로 판정하고 60도로 꺾었다. 고친 뒤 교착 완화 1527회에서 0회, 도착 시간 중앙값 11.3 s에서 8.3 s. 앞서 "CBF 교착"으로 본 꼬불거림은 대부분 이 버그였다.
  - 편대가 들어갈 수 없는 목표(벽 가까이, 기둥 위)는 거부하지 않고 닿을 수 있는 가장 가까운 점으로 옮기고 알린다. 거부 94/160에서 3/240.
  - 지금 위치에서 들어갈 공간이 없는 편대 변경은 거부한다. 서 있는 편대가 벽이나 기둥에 걸리면(편대 변경, 이륙, 기둥 추가 뒤) 들어가는 가장 가까운 점으로 옮긴다.
  - 벽도 CBF 제약에 넣었다(가장 가까운 벽 위의 점, 여유 D/2). 벽 넘음 최대 0.36 m에서 0.
  - 결과: 갇힘 0, 드론끼리 최소 0.41 m, 드론과 기둥 표면 최소 0.41 m. tests/test_dashboard.py에 축소판 무작위 시험을 넣었다.
- 남는 한계: 이상 모델(통신 지연, 잡음 없음)이다. 실측 tau와 지연으로 다시 확인해야 한다.

## 다음 단계: 실기체 모드

사용자가 정했다: 가상 모드를 먼저 만들고, 실기체 모드는 기체에 필요한 요소가 갖춰지면 만든다. 시작 조건은 아래다. 이 조건이 확인되기 전에는 착수하지 않는다.

- 호버링이 안정적으로 된다.
- 기체들이 공통 위치 좌표계를 공유한다(UWB 등).
- 노트북 한 대에서 BLE로 여러 기체를 동시에 연결하는 것이 확인된다.

그때 할 일은 실기체 백엔드 추가, 모드 전환 스위치, 드론별 배터리와 연결 상태 표시, 아래 안전 처리다.

- 가상 모드에서는 서버가 BLE 연결을 열지 않는다.
- 실기체 모드로 전환할 때 확인 창을 거친다. 실기체 모드는 화면 위쪽에 눈에 띄는 색 띠로 구분한다.
- 시작(이륙)은 확인 창을 거친다. 확인 없이 이륙 명령이 나가지 않는다.
- 중지는 그 자리 LAND다. 이륙 명령보다 항상 빨리 눌려야 하므로 확인 창이 없다.
- 비상 정지(강제 DISARM)는 별도 버튼이다. 두 번 눌러야 하고, 공중에서 쓰면 추락한다는 경고를 보인다. `n6_fly.py`의 x 두 번과 같은 방식이다.
- 화면이나 서버가 끊기면 기존 HEARTBEAT 실패 처리가 기체를 LAND시킨다. 앱이 이를 무력화하지 않는다.

## 빌더에게 맡기는 것

- 폴더 안 파일 구성, WebSocket 메시지 형식, 상태 전송 주기.
- 시뮬 파라미터(호버 고도, 상승 속도, τ, 최대 속도, 안전거리)의 기본값. `simulator.py`의 기본값을 따르는 것을 우선한다.
- 쿼드콥터 3D 모양의 세부 비율과 애니메이션.
- 편대 형태 세 가지의 좌표 정의와 가상 모드의 시작 위치 배치.
- 화면 글꼴과 버튼 모양. 파란색 그리드 배경이라는 방향만 지킨다.

## 시험

- 서버 시뮬 루프 테스트 하나: 시작 후 각 편대(일렬, 삼각, 원)를 명령하면 20초 안에 모든 드론이 자기 자리에서 0.2 m 이내로 들어오고, 그동안 드론 사이 거리가 0.3 m 아래로 내려가지 않는다. 중지 후에는 모든 드론의 z가 0이 된다.
- 화면은 브라우저로 열어 눈으로 확인한다: 인터넷을 끊은 상태에서 화면이 뜨고, 버튼마다 드론이 해당 동작을 한다.
