# A 후속 작업: 시간 정렬 분석

2026-10-14. 기존 성공 비행 로그를 재분석했다. 새 비행이나 펌웨어 변경은 하지 않았다.

## 구현

`scripts/analyze_timing.py`를 추가했다. 기록된 이륙 전 시계 offset을 SITL 부팅 시각에 더하고, 해당 시각의 Gazebo truth를 선형 보간한다. 동일 추정 타임스탬프는 한 번만 평가한다. 기록 범위 밖은 외삽하지 않으며, truth 간격이 0.3초를 넘으면 보간하지 않는다. 원래 CSV와 기존 지표를 덮어쓰지 않고 `time_aligned.csv`, `timing_metrics.json`을 생성한다.

이 방식은 표본 비교 시점을 보완한다. 이륙 전 offset 자체는 근사값이므로 완전한 시계 동기화를 입증하지는 않는다. 추정 오차를 줄이도록 offset을 다시 최적화하지 않았다.

## 결과

| 시험·기체 | 동일 평가 표본의 기존 RMSE | 시각 보간 후 RMSE | 기록 행 / 고유 추정 표본 / 평가 표본 |
|---|---:|---:|---:|
| 정사각형 0번 | 0.2251m | 0.2240m | 411 / 341 / 340 |
| 두 기체 0번 | 0.2096m | 0.2095m | 236 / 187 / 185 |
| 두 기체 1번 | 0.1134m | 0.1127m | 236 / 191 / 189 |

기존 보고서와 수치가 조금 다른 이유는 중복 추정 표본과 보간 불가능한 경계 표본을 제외했기 때문이다. 위 표는 같은 표본 집합끼리 비교했다. 이번 시각 보간만으로 오차가 크게 줄지는 않았다.

- 저장된 truth 주기: 정사각형 약8.09Hz, 두 기체 약7.72Hz.
- 정사각형 70행, 두 기체 0번49행·1번45행은 같은 추정 타임스탬프를 반복 기록했다.
- 원시 센서 전체를 저장한 로그가 아니므로 위 수치를 센서 자체 송신 주기로 단정하지 않는다.
- 일부 행은 보정된 추정 시각이 최신 truth 시각보다 앞선다. 최대 약0.079초다. 서로 다른 스트림의 최신값을 함께 기록한 방식과 근사 시계 offset의 영향을 구분해야 한다. 이를 음의 실제 통신 지연으로 해석하지 않는다.
- 추정 타임스탬프의 역행은 발견하지 않았다.
- 10Hz로 행을 인위적으로 늘리지 않았다. 원본 표본의 빈도와 결측을 먼저 보존한다.

## 실행

Ubuntu 터미널:

```bash
cd ~/capstone_design
/usr/bin/python3 scripts/test_analyze_timing.py
/usr/bin/python3 scripts/analyze_timing.py runs/a_20261013_214913
/usr/bin/python3 scripts/analyze_timing.py runs/a_20261013_214655
```

보간 테스트 3개 통과: 불규칙 시간 간격의 등속 이동, 범위 밖 외삽 차단, 큰 간격 제외와 정확한 관측 시각 보존.

## 이어서 할 일

1. 별도 수신 버퍼에 추정값과 truth의 원본 시각·호스트 수신 시각을 각각 저장해 기록 손실과 전송 주기를 분리한다. 단순 최신값 로깅의 반복 표본을 표시한다.
2. 이륙 중 생기는 오차와 광류 품질·기체 자세·방향·지연의 관계를 분석한다. 현재 분석만으로 원인을 특정하지 않는다.
3. 위치 공분산 추출은 별도 미완료 항목으로 유지한다. 현재 firmware의 비지원 메시지를 실제 공분산으로 대체하지 않는다.
