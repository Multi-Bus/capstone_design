# N6 드론 호버링 시험 절차 (4호기 진행 기록 기준)

작성일 2026-11-21 · Windows · BLE(GUIDED) · 기체별로 같은 순서를 반복한다.

이 문서는 4호기에서 호버링 시험 준비를 실제로 진행한 순서를 정리한 것이다. 팀 자료(`n6_drone_handoff_20261120.zip`의 `QUICKSTART_KO.md`, `README_KO.md`, `HANDOFF_KO.md`)와 호버링 시험 작업서의 절차를 따르고, 진행하면서 막혔던 곳과 해결 방법을 함께 적었다.

**현재 진행 상태(4호기, 2026-11-21 기준):** 통신, 펌웨어, 광류 방향, 모터 방향, 프롭 없는 안전 시험까지 끝났다. 프롭을 단 시험은 여러 번 했지만 아직 호버링에 성공하지 못했다. 이륙은 되나 고도를 유지하지 못한다. 원인은 기압계가 프롭 바람에 틀어지는 것으로 로그에서 확인했고, 높이 소스를 거리센서로 바꿔 다시 시험하는 중이다. 자세한 내용은 13장에 있다.

## 0. 원칙

- **프롭을 단 시험 전까지는 프롭을 모두 뗀다.** 시동이 걸리면 모터가 돌기 때문이다. 센서나 파라미터를 읽기만 하는 작업도 프롭을 뗀 상태에서 한다.
- 스위치와 점퍼는 **전원을 모두 끈 상태에서만** 바꾼다.
- NUCLEO 외부 플래시에 쓰는 작업은 **팀에 알린 뒤** 한다.
- 시동·이륙 키(`t`, `y`, 스페이스)는 **사람이 터미널에서 직접** 누른다. 자동 스크립트가 대신 보내지 않는다.
- 하나라도 다르게 동작하면 프롭을 단 비행을 보류하고, 화면과 FC 메시지를 그대로 공유한다.

## 1. 준비물과 환경

- Windows 10 이상 PC, BLE가 되는 어댑터(내장 또는 USB 동글), **PC 블루투스를 켜 둘 것**
- 데이터 USB-C 케이블(ST-LINK용 `CN10`, FC용 각각 필요). 충전 전용 케이블은 안 된다.
- STM32CubeProgrammer 2.24.0 (ST 공식 사이트, 로그인 필요). 기본 설치 경로는 `C:\Program Files\STMicroelectronics\STM32Cube\STM32CubeProgrammer\bin\`
- 팀 ZIP `n6_drone_handoff_20261120.zip`을 **새 폴더**에 풀고, 경로가 길면 빌드·실행이 실패할 수 있으니 짧은 경로에 둔다.
- Python 3.10 이상. 가상환경에 설치할 패키지: `bleak`, `pymavlink`, `pyserial`, `numpy`
- 이 문서의 보조 스크립트: `tools/hover_test/` (아래 각 장에서 설명)
- 멀티미터, 보안경, 나일론 안전줄 1 m 두 줄, 절연 테이프, 배터리 타이

가상환경은 ZIP을 푼 폴더(`<압축 푼 곳>`, `stm32_projects`가 들어 있는 폴더)에 만든다. 이 문서의 명령은 그 폴더를 기준으로 쓴다.


`tools\hover_test\` 아래 스크립트는 저장소 루트에서 전체 경로로 실행한다.

## 2. NUCLEO 펌웨어 확인과 복구

기체마다 NUCLEO 외부 플래시(`0x70000000`)에 브리지 펌웨어(`n6_bridge_FSBL-trusted.bin`)가 들어 있어야 한다. 확인되지 않았던 보드 세 장 중 둘에는 ST 출하 이미지가 들어 있었고, 한 장에는 이미 브리지가 들어 있었다.

### 2-1. 연결 구성 (개발 모드)

| 항목 | 상태 |
|---|---|
| 드론 배터리, FC USB | 분리 |
| NUCLEO `CN10` | PC에 데이터 케이블로 연결 (유일한 연결) |
| `BOOT1` | `2–3` |
| `CN9` | `1–2 (STLK)` |
| 캐리어 `J12 → CN8` 케이블 | 분리 |
| 확인 | `LD1(5V_PWR)`이 켜져 있어야 한다 |

### 2-2. 읽기(백업)

```powershell
$p = "C:\Program Files\STMicroelectronics\STM32Cube\STM32CubeProgrammer\bin"
& "$p\STM32_Programmer_CLI.exe" -l stlink
& "$p\STM32_Programmer_CLI.exe" -c port=SWD sn=<ST-LINK 시리얼> mode=HOTPLUG -el "$p\ExternalLoader\MX25UM51245G_STM32N6570-NUCLEO.stldr" -r 0x70000000 0x100000 <백업파일>.bin
```

읽은 파일의 앞 25,952 B를 `n6_bridge_FSBL-trusted.bin`(SHA-256 `444F1E07F68CC54AE4C6C60269F2C02537C1355D1C2C8959F3EF0921F602E014`)과 비교한다.

- 앞부분이 같으면 이미 브리지가 들어 있다. 쓰지 않는다.
- ST 출하 이미지는 1 MiB 전체의 SHA-256이 `7905C3BC…6F7D`로 나왔다(두 보드 동일).

### 2-3. 쓰기(필요할 때만, 팀에 알린 뒤)

```powershell
& "$p\STM32_Programmer_CLI.exe" -c port=SWD sn=<ST-LINK 시리얼> mode=HOTPLUG -el "$p\ExternalLoader\MX25UM51245G_STM32N6570-NUCLEO.stldr" -hardRst -w "<압축 푼 곳>\stm32_projects\nucleo\n6_bridge\STM32CubeIDE\FSBL\Release\n6_bridge_FSBL-trusted.bin" 0x70000000 -v
```

`Download verified successfully`가 나오면 통과다. 쓴 직후 바로 읽어서 다시 대조하면 `Data read failed`가 날 수 있다. 브리지가 부팅해서 외부 플래시를 쓰기 때문으로 보이며, 쓰기 실패는 아니다.

### 2-4. 연결 오류와 해결

| 증상 | 원인과 해결 |
|---|---|
| `Voltage: 0.00V`, `Unable to get core ID` | 칩에 전원이 안 들어온 상태. **`LD1(5V_PWR)`이 꺼져 있으면** 5V 레일이 안 올라온 것이다. 케이블을 바꿔 다시 꽂거나 다른 USB 포트를 쓴다. 4호기는 케이블을 바꿔 다시 꽂으니 `LD1`이 켜지고 연결됐다. 점퍼(`CN9 1–2`, `BOOT1 2–3`)는 사진으로 위치를 확인한다. |
| `Voltage`는 정상(약 3.3V)인데 `Unable to get core ID` | 브리지가 디버거 없이 돌고 있어서 코어에 붙지 못하는 상태다. `BOOT1`이 `2–3`인지, `CN9`가 `1–2`인지 확인하고 USB를 뽑았다 꽂는다. 개발 모드(`BOOT1 2–3`)로 두면 플래시에서 부팅하지 않아 읽을 수 있다. |
| 리셋하며 연결(`mode=UR`)해도 `DEV_AP_ACCESS_ERROR` | CubeProgrammer CLI로는 실행 중인 브리지의 RAM을 읽을 수 없다. 카운터를 보려면 CubeIDE 디버그 세션이 필요하다(이 문서 범위 밖). |

## 3. 비행 구성으로 전환

전원을 모두 끈 상태에서 바꾼다.

| 항목 | 상태 |
|---|---|
| `BOOT0` | `1–2` |
| `BOOT1` | `1–2` |
| `CN9` | `3–4` |
| `CN10` USB | 분리 |
| 캐리어 `J12 → NUCLEO CN8` | 연결 |
| 드론 배터리 | 연결 (프롭은 뗀 상태) |

기대 상태: NUCLEO LED1이 1초마다 짧게 깜빡이고, LED2는 꺼져 있고, XIAO LED는 둘 다 꺼져 있다(BLE 광고 중).

노트북이 연결되면 XIAO 파랑·초록이 켜지고, NUCLEO LED1이 0.5초 켜짐/0.5초 꺼짐이 된다. 단, LED1은 XIAO `D0 → NUCLEO PD11` 선이 이어져 있어야 바뀌므로 LED1이 안 바뀐다고 통신이 안 되는 것은 아니다. 통신은 4장에서 따로 확인한다.

## 4. BLE 양방향 통신 확인 (읽기 전용)

### 4-1. 광고 확인

`tools/hover_test/n6_scan.py`로 `N6-DRONE-*`가 광고되는지 본다.

- 광고가 잠깐 안 보일 수 있다. 다시 스캔한다.

### 4-2. 양방향 확인

`n6_ro_check.py`는 FC 하트비트를 받고, 파라미터 **읽기 요청**만 보낸다. 시동, 모드 변경, 모터, 파라미터 쓰기, EKF 원점 설정은 보내지 않는다.

```powershell

```

| 결과 | 의미 |
|---|---|
| 하트비트 수신 + 파라미터 값 응답(`MAV_GCS_SYSID 250`, `FS_GCS_ENABLE 5`, `FS_GCS_TIMEOUT 3`, `SERIAL4_BAUD 921`) | 양방향 정상 |
| 하트비트 수신, 파라미터 응답 없음 | 노트북→FC 방향만 막힘. 4-3 참고 |
| 하트비트도 없음 | FC 전원, NUCLEO 비행 구성, `SERIAL4` 설정 확인 |

### 4-3. 노트북→FC 방향이 막힌 경우

경로: `노트북 →BLE→ XIAO →(D6→PF6)→ NUCLEO →(PH4)→ FC RX4`.

FC USB를 PC에 꽂고 FC의 UART 통계(`@SYS/uarts.txt`, MAVLink FTP)를 읽는다. 아래처럼 **`SERIAL4 RX`가 0이면** FC 입력선에 신호가 안 들어오는 것이다.

```
SERIAL4 UART4  TX*= 3699  RX*= 0  FE=0 OE=0 NE=0
```

점검 순서:

1. FC 윗면 `Dji` 점퍼 패드(가운데 ↔ `Dji`)가 납땜돼 있는가. 열려 있으면 FC RX4가 연결되지 않는다(1호기에서 확인된 사례).
2. XIAO 선 연결. **4호기의 원인은 XIAO 배선이었다.**
3. 도통 검사: `XIAO D6 ↔ NUCLEO PF6`, `NUCLEO PH4 ↔ FC RX4(J2 2번)`. `XIAO D0 → 캐리어 J10 5번 → NUCLEO PD11`은 LED 표시용이다.

한쪽 방향만 되는 것은 방향마다 선이 따로이기 때문이다. `FC→NUCLEO→XIAO→노트북`(`PE7`, `PA2→D7`)이 되어도 `D6→PF6`, `PH4→FC RX4`가 끊겨 있을 수 있다.

## 5. FC 펌웨어와 파라미터 확인 (FC USB)

FC를 USB로 PC에 연결한다(QGC는 끈다. 같은 포트를 같이 쓸 수 없다). 포트 번호는 장치 관리자에서 확인하고, 기체마다 다르다.

- ArduCopter **4.7.3**, `type 2`(쿼드콥터), `autopilot 3`이어야 한다.
- 파라미터 전체를 읽어 팀 공통 파일 `n6_base.param`과 비교한다. 4호기는 47개 항목이 모두 일치했다.
- 반드시 확인할 값: `SERIAL4_PROTOCOL 2`, `SERIAL4_BAUD 921`, `FS_GCS_ENABLE 5`, `FS_GCS_TIMEOUT 3`, `MAV_GCS_SYSID 250`, `FRAME_CLASS 1`, `FRAME_TYPE 12`, `AHRS_ORIENTATION 12`, `RNGFND1_TYPE 10`, `RNGFND1_ORIENT 25`, `EK3_SRC1_POSXY 0`, `EK3_SRC1_VELXY 5`, `EK3_SRC1_POSZ 2`, `EK3_RNG_USE_HGT 70`, `ARMING_SKIPCHK 64`, `BATT_LOW_VOLT 14.0`, `BATT_FS_LOW_ACT 1`.
- 기체별로 다른 값: `SERVO_BLH_RVMASK`, `FLOW_ORIENT_YAW`. 아래 7·8장에서 실측으로 정한다.

## 6. 센서와 높이 확인

프롭을 뗀 상태에서 `fc_sensors.py`로 읽는다.

```powershell
.venv\Scripts\python tools\hover_test\fc_sensors.py COM37 10
```

| 항목 | 정상 값 (바닥) |
|---|---|
| 거리센서 | 약 0.04 m (`RNGFND1_GNDCLR` 0.05 m와 비슷) |
| 광류 품질 | 60 이상 |
| 롤/피치 | 수평(±1° 안쪽) |
| 전압 | 만충 16.4 V 근처 |
| 진동 | x, y, z가 수 이하, 클리핑 0 |
| **EKF 높이** | **거리센서와 0.1 m 이내** |

**EKF 높이가 어긋나는 문제.** 4호기는 재부팅 직후에는 거리센서와 0.02 m 차이였는데, 기체를 들거나 옮기면 최대 0.8 m까지 틀어졌고, 가만히 두어도 시간이 지나면서 약 0.15 m씩 어긋났다. 기압계(`EK3_SRC1_POSZ 1`) 드리프트로 보인다. 1호기가 못 뜬 것과 같은 증상이다. 0.1 m를 넘으면 비행하지 않는다.

- **재부팅 방법:** 배터리와 FC USB를 **둘 다 분리**했다가 바닥에서 연결한다. FC USB가 꽂혀 있으면 USB 전원으로 FC가 계속 켜져서 배터리만 뺐다 꽂아서는 재부팅되지 않는다.
- 재부팅 후 **30초 동안 기체를 만지지 않는다.** 기체를 들거나 옮기면 다시 어긋난다.
- 센서 시험(기울이기 등)을 끝낸 뒤 **마지막에** 재부팅해서 값을 맞춘 다음 바로 이륙한다. 재부팅 후 시간이 오래 지나면 다시 어긋난다.

## 7. 광류 방향 시험과 수정

광류 센서(MTF-01P)의 장착 방향이 `FLOW_ORIENT_YAW`와 맞는지 확인한다. 기체를 손에 들고 롤·피치를 각각 ±15° 정도 기울이면서 광류 값과 자이로를 비교한다.

`flow_phase.py`로 단계별 기록한다.

```powershell
.venv\Scripts\python tools\hover_test\flow_phase.py rec COM37 roll 18
.venv\Scripts\python tools\hover_test\flow_phase.py rec COM37 pitch 18
.venv\Scripts\python tools\hover_test\flow_phase.py analyze
```

- 롤 단계(18초): 시작 후 3초 뒤부터 기록한다. 좌우로만 약 8번 천천히 흔든다.
- 피치 단계(18초): 앞뒤로만 약 8번 천천히 흔든다.
- 판정: `flow_x`와 롤 자이로, `flow_y`와 피치 자이로의 상관이 **+0.8 이상**이면 맞는 방향이다. **-0.8 근처면 방향이 180° 틀린 것**이다.
- 4호기: `FLOW_ORIENT_YAW 0`일 때 -0.79 / -0.82였고, `18000`으로 바꾼 뒤 +0.87 / +0.91이었다. 1호기도 같은 값(0 → 18000)이었다.
- `max tilt`가 8° 미만이면 기체를 충분히 기울이지 않은 것이라 결과가 무효다.

수정은 파라미터 한 개만 쓰고 다시 읽어서 확인한다. 쓰기 전에 현재 값을 백업하고, 응답의 **파라미터 이름**을 확인한다(다른 파라미터의 응답을 잘못 읽을 수 있다).

```python
from pymavlink import mavutil
m = mavutil.mavlink_connection("COM37", baud=115200); m.wait_heartbeat()
m.mav.param_set_send(m.target_system, m.target_component, b"FLOW_ORIENT_YAW", 18000.0, 4)  # 4 = INT16
```

적용 후 FC를 재부팅하고 시험을 다시 해서 +값이 나오는지 확인한다.

## 8. 모터 방향

프롭을 뗀 상태에서 QGC의 Motors 슬라이더로 모터를 하나씩 5~10%로 2~3초 돌려 위치와 방향을 확인한다. 위에서 본 기준이다.

| QGC 순서 | 위치 | 회전 |
|---|---|---|
| 1 / A | 앞 오른쪽 | 반시계 |
| 2 / B | 뒤 오른쪽 | 시계 |
| 3 / C | 뒤 왼쪽 | 반시계 |
| 4 / D | 앞 왼쪽 | 시계 |

방향이 반대인 모터가 있으면 `SERVO_BLH_RVMASK`에 해당 비트를 더한다(1/A=2, 2/B=1, 3/C=4, 4/D=8). 4호기는 `15`이고 방향이 모두 맞았다.

```powershell
# 시험 스크립트 (팀 ZIP, 사람이 키를 누름)
cd "<압축 푼 곳>\stm32_projects\tools"
..\..\.venv\Scripts\python n6_fly.py --name "N6-DRONE-4"
```

연결되면 `BLE 연결됨`, `FC HEARTBEAT 수신`, `노트북→FC 방향 확인됨`, `페일세이프 파라미터 OK`가 나와야 한다. 키는 **영문 입력** 상태로 누른다.

**주의:** `t`는 시험 시작이 아니라 "이륙 시험을 할까?" 확인 질문을 띄운다. **`y`를 눌러야** GUIDED → 시동 → 이륙 명령이 나가고 모터가 돈다. `y` 대신 다른 키(스페이스 포함)를 누르면 취소된다.

시동 후 `DISARM_DELAY`(기본 10초)가 지나면 스스로 꺼지므로 그 안에 시험한다.

| 시험 | 방법 | 통과 기준 |
|---|---|---|
| 킬 키 | `t` → `y`, 모터가 돌면 스페이스 | `킬! LAND 3회` 표시, FC 모드 LAND, 시동 꺼짐 |
| 링크 단절 ① | 시동 후 PC 블루투스 끄기 | 약 3초 뒤 FC `GCS Failsafe` → LAND, 시동 꺼짐 |
| 링크 단절 ② | 시동 후 **XIAO를 캐리어에서 통째로(전원 포함) 뺀다** | 같음 |
| 링크 단절 ③ | 시동 후 NUCLEO 리셋 버튼 | 재부팅이 3초보다 짧으면 페일세이프가 안 걸릴 수 있다. 4호기에서는 링크 끊김이 관찰되지 않아 확인하지 못함 |
| 링크 단절 ④ | 시동 후 스크립트 **터미널 창을 X로 강제 종료** (`q`, Ctrl+C는 LAND를 먼저 보내 시험이 안 된다) | 같음 |
| 전체 시퀀스 | `t` → `y`를 끝까지 | GUIDED → 시동 → 이륙 명령 → 호버(프롭이 없어 안 뜸) → LAND → 시동 꺼짐 |

- 링크 단절 시험 뒤에는 `PreArm: GCS failsafe on`이 한동안 나온다. 스크립트를 다시 실행해 링크가 복구되면 `GCS Failsafe Cleared`로 풀린다.
- **XIAO 커넥터 시험은 양방향을 모두 끊어야 한다.** 한 방향 선(NUCLEO→XIAO)만 뽑으면 FC가 노트북 하트비트를 계속 받아서 페일세이프가 걸리지 않는다. 4호기에서 처음에는 이렇게 해서 통과로 잘못 볼 뻔했다.
- 프롭이 없으면 `Potential Thrust Loss`가 뜨는 것이 보통이다. 프롭을 달고 비행했는데도 같은 경고가 나오면 해당 모터를 점검한다.
- 이륙 명령 뒤 "8초 안에 0.70 m 도달 못 함 (현재 0.00 m)"는 프롭이 없어서 정상이다.

## 10. 호버링 시험 (프롭을 단 시험)

조건은 작업서에 세 가지가 있다. 팀과 확인하고 기록한다.

| 출처 | 높이·시간 | 비고 |
|---|---|---|
| 첫 비행 작업서 §8 | 0.8 m / 10~20초 | 관찰 후 LAND |
| 브리지 설계 §5·7 | 0.8 m / 5초 | 자동 시퀀스 기본값 (스크립트 기본) |
| 인수인계 §6·빠른 시작 §7 | **0.5 m / 3초, 안전줄 사용** | 가장 최근 재시험 조건. 이 문서는 이 조건을 권한다 |

순서:

1. 배터리를 분리하고 프롭을 단다. A·C는 반시계용, B·D는 시계용이다. 둥근 앞전이 회전 방향으로 먼저 지나가고 볼록한 면(글씨 면)이 모터를 보게 단다. 손으로 돌려 덕트에 닿는지 확인한다.
2. 배터리는 기체 중심에 놓고 고무판을 댄다. 폭 3 mm 이하 타이를 앞뒤 슬롯에 걸어 움직이지 않을 정도로만 조인다. 잘라낸 끝은 절연 테이프로 덮는다. 선이 덕트에 닿지 않게 한다.
3. 시험장: 주변 3 m 이상을 비운 밝은 실내, 무늬 있는 바닥(단색이면 테이프나 매트로 무늬를 만든다). 조작자는 보안경을 쓰고 3 m 뒤에 선다. 안전줄 1 m 두 줄을 양옆 무거운 물체에 고정한다. 줄은 팽팽하지 않게, 바닥으로 늘어지거나 거리센서 아래로 들어가지 않게 한다.
4. **마지막에 재부팅**한다. 배터리와 FC USB를 모두 분리했다가 **배터리만** 바닥에서 연결하고 30초 기다린다. `n6_fly` 상태줄의 `EKF높이`와 `거리센서` 차이가 **0.1 m 이내**인지 확인한다. 아니면 이륙하지 않는다.
5. 실행:

```powershell
cd "<압축 푼 곳>\stm32_projects\tools"
..\..\.venv\Scripts\python n6_fly.py --name "N6-DRONE-4" --alt 0.5 --hover 3
```

6. `t` → `y`. 조작자는 킬 키(스페이스)에 바로 손이 닿게 한다.
   - 한 방향으로 계속 흐르거나 가속하면 즉시 LAND(스페이스).
   - 심하게 흔들리거나 뒤집히려 하거나 줄이 팽팽해지면 즉시 중단한다.
   - `x`를 1초 안에 두 번 누르면 강제 정지다. 공중에서는 추락하므로 바닥이나 정말 위험할 때만 쓴다.
7. 착지 후 시동 OFF를 확인한다. 5초가 넘게 시동이 켜져 있으면 `x x`.
8. 시험 중 "FC 응답 없음 3초 이상"이 뜨면 스크립트가 시험을 중단한다. 자동으로 GUIDED로 되돌리지 않으므로 필요하면 스페이스(킬)를 누른다.

**1호기의 지난 시도 (참고).** 프롭을 단 시험에서 거리센서가 0.02 m에 머물고 EKF 높이만 올라 뜨지 못한 기록이 있다. 4호기도 같은 이유로 안 뜰 수 있다. 억지로 올리지 말고 LAND한 뒤 로그를 모은다.

## 13. 프롭 호버링 시험 진행 기록 (4호기, 2026-11-21)

### 13-1. 무슨 일이 있었나

프롭을 달고 `--alt 0.3`으로 여러 번 시험했다. 모터가 돌고 기체가 살짝 뜨지만, 곧 바닥으로 내려오고, 착지한 뒤에도 시동이 꺼지지 않았다. FC 내부 로그를 받아 분석한 결과는 다음과 같다.

| 로그 | 실제 높이(거리센서) 최대 | EKF 높이 최대 | 기압 높이 최대 | EKF와 실제의 최대 차이 |
|---|---|---|---|---|
| 1 | 0.22 m | 1.61 m | 2.67 m | 1.26 m |
| 2 | 0.29 m | 1.08 m | 3.08 m | 1.06 m |
| 3 | 0.56 m | 1.53 m | 2.46 m | 1.48 m |
| 4 | 0.49 m | 0.94 m | 2.32 m | 0.85 m |
| 5 | 0.88 m | 1.25 m | 2.41 m | 0.39 m |

- **원인:** 모터가 돌기 시작하면 0.5초 안에 기압 높이가 1~2 m로 튄다. 이때 실제 높이는 0.1~0.2 m다. 덕트 안에서 프롭 바람 때문에 FC의 기압계가 틀어지는 것이다. EKF가 기압계를 따라가므로 FC는 목표 높이에 도달했다고 믿고 스로틀을 줄인다. 그래서 "처음에는 잘 올라가는데 유지하지 못하고 떨어진다".
- **착지 후 시동이 안 꺼지는 이유:** EKF 높이가 실제보다 높아서 FC가 착지했다는 것을 인식하지 못한다. 이때는 킬 키(`x`를 1초 안에 두 번)로 강제 정지한다.
- `EK3_RNG_USE_HGT 70`(저고도에서 거리센서 사용)은 이미 켜져 있었지만 EKF는 여전히 기압계에 끌려갔다.
- 로그 5(가장 최근)에서는 처음으로 약 0.8 m까지 떠서 10초쯤 버텼다. 그래도 EKF 높이가 실제보다 0.4 m 높았다.
- 모터는 최대 출력 근처(PWM 1949)까지 올라갔고 스로틀 호버 값은 약 0.39~0.42로 학습됐다. 추력이 부족한 것은 아니다.

### 13-2. 바꾼 것

| 항목 | 이전 | 이후 | 이유 | 비고 |
|---|---|---|---|---|
| `EK3_SRC1_POSZ` | 1 (기압계) | **2 (거리센서)** | EKF가 기압계에 끌려가는 것을 막는다 | 4호기만. `fc/drones/drone4.param`에 기록. 재부팅(배터리와 FC USB 모두 분리) 후 적용 |
| `BATT_FS_LOW_ACT` | 1 (착륙) | **0 (동작 없음)** | 시험 중 전압 처짐으로 저전압 착륙이 걸리는 것을 막는다 | **임시. 시험이 끝나면 1로 복구** |

- 거리센서는 최대 8 m까지 본다. 그 위나 센서가 무효일 때 기압계로 돌아가는지는 확인하지 않았다. 지금 시험은 2 m 이하다.
- 높은 고도에서 기압계로 되돌리려면 EKF 소스 세트 2를 기압계로 쓰고 전환하는 방법이 있다(MAVLink 명령이나 RC 스위치). 세트 2의 `VELXY`와 `YAW`가 현재 0이라서 세트 1과 같게 맞춘 뒤에 써야 한다. 이번에는 적용하지 않았다.

### 13-3. 배터리 (로그 5에서 확인)

- 시험 중 전압이 14.6 V에서 11.6 V까지 내려갔다. 이때 쓴 용량은 3300 mAh 중 약 115 mAh(3.5%)뿐이었다.
- 전원을 켠 직후 대기 전압이 14.9 V였다. 4S 완충(16.8 V)보다 많이 낮은, 충전량이 낮은 상태로 시작한 것이다. 호버링 전류가 약 20~24 A(최대 30 A)여서 전압이 크게 처졌다.
- 저전압 failsafe(`BATT_LOW_VOLT 14.0`, 동작 착륙, 지속 10초)가 걸려서 12.5 V에서 착륙했다.
- **다음 시험은 완충한 배터리로 한다.** 2 A 충전기로 약 1~1.5시간 걸린다. 충전할 때 충전기에서 셀별 전압과 내부 저항을 확인한다.
- 로그 5에 `Potential Thrust Loss (3)` 경고가 있다. 3번 모터를 따로 점검해야 한다.
- 비행 사이에 착지 직후 대기 전압을 재고, 14.0 V 아래이면 그 배터리로는 더 시험하지 않는다.

### 13-4. 로그 6: 시동 거부 (2026-11-21)

`POSZ 2`로 바꾼 뒤 처음 시험하려 했으나 시동이 걸리지 않았다. 로그 6(49초)에는 시동 이벤트가 없고 모터 출력은 내내 1000이다. FC 메시지는 `PreArm: Battery 1 low voltage failsafe`와 `Arm: Battery 1 low voltage failsafe`다.

- FC가 읽은 배터리 전압이 5.7 V였고 26초 동안 5.35 V로 천천히 내려갔다. 이후 읽은 값은 0.5 V였다. 실제 4S 배터리는 14~16.8 V이므로, 배터리가 FC 전원 입력에 연결되지 않은 것이다(USB 전원만 들어온 상태).
- `BATT_FS_LOW_ACT 0`은 비행 중 동작만 바꾼다. 시동 전 검사는 전압이 `BATT_LOW_VOLT`(14.0 V) 아래이면 그대로 거부한다.
- 이 로그로는 `POSZ 2`의 효과를 확인하지 못했다. 비행 기록이 없다.
- 확인할 것: 배터리 단자 전압(멀티미터나 충전기), 배터리 커넥터(XT60)와 전원선·전원 분배 보드 접촉. 배터리를 꽂았을 때 FC가 14 V 이상으로 읽는지 본 다음에 시험한다.

### 13-5. 현재 상태와 다음 할 일

- 4호기는 `POSZ 2`와 `BATT_FS_LOW_ACT 0`(임시)이 적용된 상태다. 배터리를 충전하고 있어서 시험은 중단했다. 높이 소스 변경의 효과는 아직 확인하지 못했다.
- 시험 후 로그에서 EKF 높이가 거리센서를 따라가는지 확인한다(`logwin.py`).
- 시험이 끝나면 `BATT_FS_LOW_ACT`를 1로 되돌린다.
- 3번 모터 추력 손실 경고 원인 확인.
- 다른 기체(1~3, 5, 6호기)에도 같은 문제가 있을 수 있다. 기압계가 프롭 바람에 틀어지는지는 기체와 덕트 구조에 따라 다르므로, 각 기체에서 이륙 전 로그로 확인한다.

### 13-6. `POSZ 2` 호버 결과와 반영 (2026-11-23)

- 4호기를 `EK3_SRC1_POSZ 2`로 다시 시험했다. 저고도에서도 높이를 안정적으로 유지했다.
- 첫 시동에서 `Arm: Gyros inconsistent`로 시동이 거부됐다. 재부팅 후 기체를 건드리지 않고 기다린 뒤 시험했다.
- `EK3_SRC1_POSZ 2`를 `fc/base/n6_base.param` 공통값으로 옮겼다. 모든 기체에 적용한다.
- `BATT_FS_LOW_ACT`는 기준값 1(착륙)로 되돌렸다. `fc/drones/drone4.param`에서 임시값을 지웠다.

## 14. 3호기와 5호기 점검 기록 (2026-11-23)

4호기와 같은 순서로 프롭 없는 점검을 했다. 두 기체 모두 프롭을 단 시험은 아직 하지 않았다.

| 항목 | 3호기 | 5호기 |
|---|---|---|
| FC 펌웨어 | ArduCopter 4.7.3 (git `d9c5097c`) | 같음 |
| 공통 파라미터 | `n6_base.param` 47개 일치. 전체 1265개 백업 | 일치 |
| NUCLEO 외부 플래시 | ST 출하 이미지였음 → 브리지 쓰기, 검증 통과 | 같음 |
| BLE | `N6-DRONE-3` 양방향 정상 | `N6-DRONE-5` 양방향 정상 |
| 센서 (배터리 연결) | 16.6 V, 광류 품질 74, 진동 0 | 16.5 V, 광류 품질 69, 진동 0 |
| EKF 높이 vs 거리센서 | 0.015 m vs 0.02 m (정상) | **0.55 m vs 0.02 m (0.53 m 차이)** |
| 광류 방향 | 0일 때 -0.80/-0.75 → `FLOW_ORIENT_YAW 18000`으로 변경 | 18000에서 +0.95/+0.94 |
| 모터 방향 | 모두 맞음 (`SERVO_BLH_RVMASK 15`) | 모두 맞음 (15) |
| 프롭 없는 안전 시험 | 통과 (아래) | 하지 않음 |
| 상태 | 호버 시험 대기 | 납땜 수리 후 재점검 |

### 14-1. 진행하면서 막힌 것

- **3호기 NUCLEO 연결:** `mode=HOTPLUG`로는 개발 모드에서도 `Unable to get core ID`가 계속 났다(전압 3.27 V 정상). 리셋하며 연결(`mode=UR reset=HWrst`)하니 읽기와 쓰기가 모두 됐다.
- **3호기 피치 광류 상관:** 18000으로 바꾼 뒤 롤은 +0.81이었지만 피치는 두 번 모두 +0.67~0.68로 기준 +0.8에 못 미쳤다. 센서 내부 자이로(`rate_y`)는 +0.92였고, 부호가 0일 때와 반대로 바뀌어서 방향은 18000으로 확정했다. 손으로 흔들 때 기체가 앞뒤로 같이 움직인 영향으로 보이나 확인하지 않았다. 호버 로그에서 수평 흐름을 다시 본다.
- **5호기 EKF 높이:** 기압계(`EK3_SRC1_POSZ 1`) 드리프트로 보인다. 재부팅 후 다시 확인하지 못했다. 공통값이 `POSZ 2`로 바뀌었으므로(13-6) 수리 후 새 공통값으로 다시 확인한다.
- **배터리를 연결하는 중 FC USB가 빠져** 포트가 사라진 적이 있다. 다시 꽂으면 같은 COM 번호로 돌아온다.

### 14-2. 3호기 프롭 없는 안전 시험 (`fc_monitor.py` 기록)

| 시험 | 결과 |
|---|---|
| 킬 키 (2회) | 시동 → 킬 → LAND → 약 4~5초 뒤 시동 OFF |
| 링크 단절 ① PC 블루투스 끄기 | BLE 끊김 약 2.3초 뒤 FC `GCS Failsafe`, LAND, 시동 OFF |
| 링크 단절 ② XIAO 통째로 분리 | FC `GCS Failsafe`, LAND, 시동 OFF |
| 링크 단절 ④ 터미널 창 닫기 | 스크립트가 창 닫힘을 Ctrl-C로 받아 LAND를 먼저 보냈다. 약 3.1초 뒤 FC `GCS Failsafe - Disarming`으로 시동 OFF |
| 비상 정지 `x x` | 강제 DISARM 동작 |
| 전체 시퀀스 | GUIDED → 시동 → 이륙 명령 → 호버 5초 → LAND → 시동 OFF, `시험 완료` |

- 링크 단절 ④는 창을 X로 닫아도 스크립트가 LAND를 보낸다. 페일세이프만 따로 보려면 ①이나 ②를 쓴다.
- `Potential Thrust Loss (4)`는 프롭이 없어서 나는 경고다. 프롭을 달고 날 때도 나오면 4번 모터를 점검한다.

## 부록. 보조 스크립트 (`tools/hover_test/`)

모두 읽기 전용이거나 스트림 속도만 바꾼다. 아래 표에 없는 동작(시동, 모드 변경, 모터, 파라미터 쓰기)은 하지 않는다.

| 파일 | 용도 | 보내는 것 |
|---|---|---|
| `n6_scan.py` | `N6-DRONE-*` BLE 광고 확인 | 없음 (스캔만) |
| `n6_ro_check.py` | BLE 연결, FC 하트비트 수신, 파라미터 읽기 | GCS 하트비트(`--hb` 옵션 시), 파라미터 읽기 요청 |
| `fc_sensors.py` | FC USB로 거리센서·광류·EKF 높이·자세·전압·진동 읽기 | 스트림 속도 요청 |
| `flow_phase.py` | 광류 방향 시험(기록과 분석) | 메시지 간격 설정(런타임) |
| `fc_monitor.py` | FC USB로 시동·모드·STATUSTEXT를 시각과 함께 기록 | 스트림 속도 요청 |
| `fc_rec.py` | 모터 출력, EKF 높이, 거리센서, 자세, 전압을 10 Hz로 CSV 기록 | 스트림 속도 요청 |
| `fc_logdl.py` | FC 내부 로그(`.bin`) 목록과 다운로드 (`list`, `get <번호> <파일>`) | 로그 요청 (지우기는 하지 않음) |
| `logsum.py`, `logwin.py`, `logts.py` | 받은 로그 분석: 요약, 시동 구간별 실제 높이와 EKF 높이 비교, 시계열 | 없음 (파일만 읽음) |
| `xiao_version.py` | BLE 알림 크기로 XIAO 릴레이 버전(v1/v2) 구분 | 없음 (수신만) |
| `fc_setparam.py` | 파라미터 하나를 바꾸고 읽어 확인. 시동 중이면 거부 | 파라미터 쓰기 (사용자가 요청했을 때만) |

`n6_ro_check.py`에는 `READ`로 읽을 파라미터 목록이 있다. 4.7에 없는 이름(예: `ARMING_CHECK`)을 요청하면 엉뚱한 응답(`STAT_RUNTIME`)이 올 수 있으니 무시한다.
